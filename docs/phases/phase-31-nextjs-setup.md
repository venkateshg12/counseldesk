## 5. Concepts

**App Router.** Folders under `src/app` are URL segments; a `page.tsx` makes a segment a page; a
`layout.tsx` wraps every page below it and persists across navigation. `[slug]` is a dynamic segment,
`[...slug]` catches several. This replaces e-commerce's `router.tsx`: the route tree _is_ the folder
tree.

**Server and Client Components.** By default a component renders on the server: it can read files and
call databases, and ships no JavaScript to the browser. A file starting with `"use client"` is a Client
Component: it can use state, effects and browser APIs, and its code is sent to the browser. The firm's
pages are pure content → Server Components, rendered to static HTML at build time. The staff pages
need state, React Query and the Axios interceptor → Client Components.

**`serverExternalPackages`.** Next bundles server code by default. `@repo/content` finds its markdown
files relative to its own location on disk (`new URL("../pages/", import.meta.url)`); bundled, that
location would be the bundle's, not the package's. Listing it in `serverExternalPackages` makes Next
load it with Node's normal import at build time, so the path resolves to `packages/content/pages`.

**`NEXT_PUBLIC_` variables.** Variables prefixed `NEXT_PUBLIC_` are inlined into the browser bundle at
build time; others exist only on the server. The API URL is public by nature (the browser calls it), so
`NEXT_PUBLIC_API_URL`. Changing it means rebuilding, which matters on Vercel.

**Why one app for site and staff.** The spec asks for "the demo law firm site and staff page" on
Next.js. Two apps would mean two deployments and two sets of config for one small staff screen. One
app, two route groups (`/` content, `/staff/*` tools), one deploy.

### Step 2 — Config files

`next.config.ts`:

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // Loaded with Node's own import at build time, so it finds its markdown files on disk.
  serverExternalPackages: ["@repo/content"],
};

export default nextConfig;
```

`tsconfig.json`:

```json
{
  "extends": "@repo/typescript-config/nextjs.json",
  "compilerOptions": {
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "paths": { "@/*": ["./src/*"] }
  },
  "include": [
    "next-env.d.ts",
    "src/**/*.ts",
    "src/**/*.tsx",
    ".next/types/**/*.ts"
  ],
  "exclude": ["node_modules"]
}
```

The `@/*` alias is e-commerce's client convention. Next may add entries to this file the first time it
runs (for example under `include`); keep what it adds.

`eslint.config.js`:

```js
import { nextJsConfig } from "@repo/eslint-config/next-js";

export default nextJsConfig;
```

`postcss.config.mjs` (from Next's docs for Tailwind v4):

```js
export default {
  plugins: {
    "@tailwindcss/postcss": {},
  },
};
```

`.env.example`:

```bash
# Where the API runs. Inlined into the browser bundle at build time.
NEXT_PUBLIC_API_URL=http://localhost:4000
```

## 9. Common mistakes

- **Putting `"use client"` at the top of the layout** "to make things work". Every page under it becomes
  client-rendered and ships its JavaScript. Keep the boundary as low as possible.
- **Forgetting `serverExternalPackages`.** The build fails to find the pages, or finds none, in Phase 32.
- **Server secrets in `NEXT_PUBLIC_` variables.** They're published in the JavaScript bundle.
- **A separate React or TypeScript version from the rest of the repo.** Pinned the same everywhere.

## 10. Interview prep

**Q: Why Next.js for this?**
A: The firm's site is static content that should render as plain HTML with real headings and anchors
(citations link to them), which Next generates at build time with Server Components; the staff pages
are a small client-side app in the same project, so one deploy covers both.

**Q: Server vs Client Components?**
A: Server Components render on the server and ship no JS — the content pages. Client Components are for
interactivity — the staff tables, forms, and React Query. I keep the `"use client"` boundary as deep as
possible.
