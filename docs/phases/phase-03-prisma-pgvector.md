# Phase 03 — Prisma 8 and pgvector wiring

## 1. Goal

Connect the API to Postgres the way the e-commerce Postgres port does — Prisma 8 with one shared
`pg.Pool` — plus the pgvector extension, and ship the first real migration: a `page` table for the
law firm's website pages.

At the end, the server refuses to start without a reachable database, `/health` reports Postgres
up or down (503 when down), shutdown closes the database last, and the `vector` extension is
installed by a migration rather than by hand.

## 2. What I will understand after this phase

1. Prisma 8's workflow: the contract file, `contract emit`, `migration plan`, `db migrate`,
   `db verify`, and what each writes.
2. What a connection pool is, why there is exactly one per process, and who is responsible for
   closing it.
3. How a Postgres extension (pgvector) gets installed through migrations, so every environment —
   laptop, CI, Neon — ends up identical.
4. Why timestamps are `TimestamptzString` here and not `Timestamptz`.

## 3. Prerequisites

- `docker compose up -d --wait` shows `counseldesk-postgres` healthy.
- `apps/api/.env` has `DATABASE_URL=postgresql://counseldesk:counseldesk@localhost:5433/counseldesk`.

## 5. Concepts

**Prisma 8's contract workflow.** You describe tables in `contract.prisma`. `prisma contract emit`
compiles it into `contract.json` (what the runtime and the migration planner read) and
`contract.d.ts` (the TypeScript types your editor uses). `prisma migration plan --name x` compares
the new contract with the last migrated one and writes a migration package under
`migrations/app/<timestamp>_x/` (`migration.ts` plus generated JSON). `prisma db migrate` applies
pending packages to the database inside **one transaction** — if any step fails, nothing changes —
and records which contract version the database is now at (a "marker" row in the
`prisma_contract` schema). `prisma db verify` checks the live database against the contract. All of
these files are committed: the migration packages are the history of your schema.

**One pool per process.** Opening a Postgres connection costs a TCP handshake, TLS, and
authentication — tens of milliseconds, more to a hosted database. A pool keeps a few connections
open and lends them to queries. One pool per process, created once at import: creating pools per
request would open new connections constantly and exhaust the server's connection limit. The ORM
and the hand-written SQL in later phases (search, RRF) share the same pool.

**Who closes the pool.** Prisma's docs state that `db.close()` releases only what Prisma created. We
create the `pg.Pool` ourselves and pass it in, so **we** must call `pool.end()`. (The e-commerce
port calls only `db.close()`; its pool is never closed and the process only exits because of
`process.exit`.)

**Extensions through migrations.** The pgvector extension pack adds a `vector` column type to the
contract and ships a baseline migration that runs `CREATE EXTENSION IF NOT EXISTS vector`. Because
it's a migration, a fresh laptop database, the CI database and Neon all get it the same way, with no
"remember to run this SQL first" step.

**`TimestamptzString`.** Prisma 8 maps `Timestamptz` columns to the JavaScript `Temporal` API, which
Node only has built in from 26.8.2. On Node 22 the first read of such a column throws. The port
used `TimestamptzString` (Postgres's own text form, an ISO string), which needs nothing extra. Same
here.

## 6. Steps

### Step 1 — Install

```bash
pnpm --filter api add @prisma/orm-postgres@8.0.0-rc.14 @prisma/orm-extension-pgvector@8.0.0-rc.14 @prisma/cli-engine@0.6.2 pg@^8.23.1
pnpm --filter api add -D prisma@8.0.0-rc.20 @types/pg@^8.23.1
```

Exact versions (no `^`) for the release-candidate packages: an RC can change between versions, and
`rc.20` of the CLI is the build that ships against the `rc.14` runtime (both depend on
`@prisma/orm-toolchain@8.0.0-rc.14` and `@prisma/cli-engine@0.6.2`). pnpm also installs
`temporal-polyfill`, a required peer of `@prisma/orm-postgres`.

### Step 2 — `DATABASE_URL` in `env.ts`

```ts
export const DATABASE_URL = getEnv("DATABASE_URL");
```

### Step 3 — `prisma.config.ts` (package root, `apps/api/`)

ADAPT the port's file. Change: add the pgvector control descriptor to `extensions`.

```ts
import "dotenv/config";
import { setDefaultResultOrder } from "node:dns";
import { setDefaultAutoSelectFamily } from "node:net";
import { definePrismaConfig } from "@prisma/cli-engine";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";
import pgvector from "@prisma/orm-extension-pgvector/control";

// The Prisma CLI loads this file but not src/config/db.ts, so apply the same IPv4 pin here.
// Without it, WSL2 (no IPv6 route) times out connecting to Neon (Phase 30).
setDefaultResultOrder("ipv4first");
setDefaultAutoSelectFamily(false);

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
    extensions: [pgvector],
    db: {
      connection: process.env["DATABASE_URL"]!,
    },
  }),
});
```

Prisma's docs write `@internal/extension-pgvector/control` and `@internal/postgres/config`; those
are the internal names. The published packages are `@prisma/orm-extension-pgvector` and
`@prisma/orm-postgres`, which is what the e-commerce port imports.

The config reads `process.env` directly instead of `env.ts` because the CLI runs this file on its
own, not as part of the server.

### Step 4 — The first contract

`src/prisma/contract.prisma`:

```prisma
// use prisma-8

// One page of the demo firm's website. `path` is the URL path on the site ("/practice-areas/dui"),
// which is also what a citation links to.
model Page {
    id          Uuid              @id @default(uuid())
    path        String            @unique
    title       String
    // sha256 of everything that decides this page's stored sections (its markdown, the split depth
    // and the embedding model — Phase 11), so re-running ingestion can skip unchanged pages.
    contentHash String
    createdAt   TimestamptzString @default(now())
    updatedAt   TimestamptzString @default(now())
}
```

The first line tells the Prisma language server which dialect the file is in. Indentation follows the
port's contract file.

Prisma 8 names the table after the model with a lowercase first letter: model `Page` → table
`"page"`. You'll write that name in raw SQL in Phase 12.

`updatedAt` has a default but no automatic update. Code that changes a page sets it (only ingestion
does, in Phase 11). The port added a trigger for this; one writer doesn't justify one here.

### Step 5 — Scripts

Add to `apps/api/package.json` `"scripts"`, following the port's names:

```json
"db:emit": "prisma contract emit",
"db:plan": "prisma contract emit && prisma migration plan --name",
"db:migrate": "prisma db migrate",
"db:verify": "prisma db verify",
"db:sql": "tsx src/scripts/write-migration-sql.ts"
```

Copy `e-commerce/apps/backends/postgres/src/scripts/write-migration-sql.ts` unchanged. Prisma 8
applies migrations from `ops.json` and doesn't write a `.sql` file; this script asks the CLI for each
migration's SQL and saves a readable `migration.sql` beside it, for review. It reads only; it is not
what `db migrate` applies.

### Step 6 — Plan and apply

```bash
cd apps/api
pnpm db:plan add_page      # emit, then plan from an empty database
pnpm db:migrate            # apply in one transaction
pnpm db:sql                # write migration.sql files for reading
pnpm db:verify             # live database matches the contract
```

Open the generated `migrations/app/*_add_page/migration.sql` and read it. You should see the
`CREATE TABLE "public"."page"`, its primary key and the unique index on `path`. Reading the generated
SQL before applying it is the habit the port's plan calls "practising Postgres, not just Prisma".

The pgvector pack's baseline migration lives in a sibling folder managed by the package. You don't
write or edit it; `db migrate` applies it.

### Step 7 — `src/prisma/db.ts`

ADAPT the port's file. Changes: register the pgvector **runtime** descriptor (the control descriptor
in the config is for the CLI; the runtime needs its own so it can read and write `vector` values),
build the pool from the validated `DATABASE_URL`, `.js`-style type import.

```ts
import pg from "pg";
import postgres from "@prisma/orm-postgres/runtime";
import pgvector from "@prisma/orm-extension-pgvector/runtime";
import type { Contract } from "./contract.js";
import contractJson from "./contract.json" with { type: "json" };
import { DATABASE_URL } from "../constants/env.js";

// One pool shared by the ORM and by hand-written SQL (health check, search).
export const pool = new pg.Pool({ connectionString: DATABASE_URL });

export const db = postgres<Contract>({
  contractJson,
  pg: pool,
  extensions: [pgvector],
});

// Every model lives in the `public` schema, so callers write `orm.Page` instead of
// `db.orm.public.Page`.
export const orm = db.orm.public;
```

`import type { Contract } from "./contract.js"` resolves to `contract.d.ts`: TypeScript looks for
`contract.ts`, then `contract.d.ts`. `with { type: "json" }` is required by Node for JSON imports in
ES modules; without it Node refuses to load the file.

### Step 8 — `src/config/db.ts`

ADAPT the port's file. Change: `closeDB` also ends the pool (see Concepts), and logging uses the
logger.

```ts
import { setDefaultResultOrder } from "node:dns";
import { setDefaultAutoSelectFamily } from "node:net";
import { db, pool } from "../prisma/db.js";
import { logger } from "../utils/logger.js";

// Node races IPv4 and IPv6 for every new connection. Where there is no real IPv6 route (WSL2,
// some containers) the IPv6 attempts lose silently and connections time out intermittently.
setDefaultResultOrder("ipv4first");
setDefaultAutoSelectFamily(false);

export const connectDB = async () => {
  await db.connect();
  // db.connect() binds the runtime; this proves a real connection can be made right now.
  await pool.query("SELECT 1");
  logger.info("connected to postgres");
};

export const closeDB = async () => {
  await db.close();
  // We created the pool, so we end it. db.close() leaves caller-owned pools open.
  await pool.end();
};

export { db, pool };
```

### Step 9 — Health and lifecycle

In `src/app.ts`, replace the health route:

```ts
import { pool } from "./config/db.js";
import { SERVICE_UNAVAILABLE } from "./constants/http.js";
// …
app.get("/health", async (_req, res) => {
  const postgresUp = await pool.query("SELECT 1").then(
    () => true,
    () => false,
  );

  res.status(postgresUp ? 200 : SERVICE_UNAVAILABLE).json(
    ok({
      status: postgresUp ? "ok" : "degraded",
      postgres: postgresUp ? "up" : "down",
    }),
  );
});
```

A health check that says "ok" while the database is down keeps a load balancer sending traffic to an
instance that can't answer anything (the e-commerce comment says exactly this).

In `src/index.ts`:

```ts
import { connectDB, closeDB } from "./config/db.js";
// in main(), before createApp():
await connectDB();
// in shutdown(), after the server has closed:
await new Promise<void>((resolve) => server.close(() => resolve()));
await closeDB();
```

Order matters: connect before listening, so no request arrives at a server that can't reach its
database; close the database after the server has drained.

## 9. Common mistakes

- **Editing `contract.json` or `contract.d.ts` by hand.** They are overwritten by `contract emit`.
  Edit `contract.prisma`.
- **Forgetting to emit after a contract edit.** Types and `migration plan` see the old shape. Use
  `pnpm db:plan`, which emits first.
- **Editing `ops.json` / `migration.json` of a planned migration.** `db migrate` fails with
  `MIGRATION.HASH_MISMATCH`. Only `migration.ts` is edited by hand, and then re-emitted by running it.
- **Using `db update` "because it's faster".** It applies the contract without writing a migration,
  so CI and Neon have nothing to replay. Use `migration plan` + `db migrate` always in this project.
- **Registering pgvector only in `prisma.config.ts`.** Migrations work, but reading or writing a
  `vector` column at runtime fails. The runtime needs `extensions: [pgvector]` in `db.ts` too.
- **Writing `Page` in raw SQL.** The table is `"page"`.
- **Not ending the pool** in scripts (seed, ingest): the script finishes its work and then hangs,
  because open pool connections keep Node alive. Every script calls `closeDB()`.

## 10. Interview prep

**Q: How do you manage schema changes?**
A: The schema is a contract file; each change is planned into a migration package that is reviewed
(I generate and read its SQL) and committed. Deploys apply pending migrations in one transaction, so
a failed migration leaves the database unchanged, and a marker records which version it's at.

**Q: Why a connection pool, and why only one?**
A: Opening connections is slow and Postgres caps how many you can have. One pool per process reuses
a few open connections; a pool per request would hit the cap under load.

**Q: How did you install pgvector?**
A: As a migration from the extension pack, not by hand, so every environment gets it identically
and a fresh database is reproducible from the repo alone.

**Q: What's the risk of building on a release-candidate ORM?**
A: APIs can change between RCs. I pinned exact versions, kept raw SQL for the parts that matter
most (search), and read the generated SQL for every migration so I'm never relying on behaviour I
haven't seen.
